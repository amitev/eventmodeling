# Event Modeling Agent — Requirements

The `em-cli agent` command and its server connection. Shared CLI rules: [SERVER.md](./SERVER.md#2-cli). Board controls: [MODELING_BOARD.md](./MODELING_BOARD.md#13-connected-clis).

Rule IDs retain their original numbers.

## CLI and sessions

- **S2.16** `npx em-cli agent --model <model> --type <type> [--name <name>]` connects to a running board server on localhost until Ctrl+C or S2.25. Report connection errors to stderr; retry as S2.32.
- **S2.17** `agent -p` or `agent --port`: use the default and error behavior of [S2.2](./SERVER.md#2-cli), but require a port in 1–65535.
- **S2.18** `GET /api/agent/events?model=<model>&agentType=<type>&name=<name>&harness=<harness>` opens a server-sent event stream; `name` and `harness` are optional. Trim supplied name/model; blank or repeated query values or missing model: 400. Type follows S2.28; harness follows S2.33. No demo messages.
- **S2.19** `agent` requires `--model <model>`. `--name <name>` is optional. Trim supplied values; blank values or missing model: exit 1 with usage. Send model and any supplied name to S2.18.
- **S2.20** Keep live sessions in memory per server. Assign each connection a new UUID; remove it on disconnect. Names must be unique, ignoring case and surrounding spaces. Reject explicit duplicates with 409; release names on disconnect or stop.
- **S2.21** `GET /api/agents` returns `[{ id, name, model, agentType, harness, lastPing, building }]` for live sessions in connection order with `Cache-Control: no-store`. `building`: slice name of the session's running build task (S2.37), else `null`.
- **S2.22** Not used (was: forward board messages).
- **S2.23** Not used (was: validate board messages).
- **S2.24** On connect and every 30 seconds send a `ping` event with `{ id, nonce }`; skip a backed-up stream. CLI posts `{ nonce }` to `/api/agents/:id/ping`. A matching unused nonce sets `lastPing` to server epoch milliseconds and returns 204; invalid nonce: 400, missing session: 404. `lastPing` starts `null`.
- **S2.25** `DELETE /api/agents/:id` removes the session, ends only its stream with a `stop` event, and returns 204. Missing session: 404. On `stop`, CLI prints `Agent stopped from the board.` to stdout and exits 0.
  - **Learning (implementation):** Report unexpected EOF only after reading the whole stream, not after a heartbeat or a chunk.
- **S2.26** Without `--name`, server atomically picks an unused surname: `Mozart`, `Haydn`, `Schubert`, `Strauss`, `Bruckner`, `Mahler`. Each available name has equal probability. All taken: 409 with a request for an explicit unique name.
- **S2.27** `cli/agent/agent.js` owns the agent client: connection, event handling and heartbeat acknowledgments. `cli/index.js` parses and validates CLI options, then calls `runAgent()`. `cli/board/agent-api.js` owns name assignment, uniqueness and agent, build-queue and modeling-task routes. `cli/board/build-queue.js` owns build-queue state (S2.36–S2.39).
- **S2.28** Require `--type`: exactly `modeler` or `builder`. Missing or invalid: exit 1 with usage. Reject old `--agent-type` flag. Send as `agentType`; server rejects missing, repeated or invalid values with 400.
- **S2.29** After accepting a successful event-stream response, CLI prints `Agent connected to http://localhost:<port>.` once to stdout. Failed connections do not print it.
- **S2.30** `POST /api/agents/:id/run` sends a `run` event only to that live session. Return 202 when queued to its stream, 404 if gone, 503 if backed up. Accept no caller-supplied command or arguments.
- **S2.31** On `run`, log the harness check. Spawn the configured harness with `-p "What model are you" --model <configured model> --output-format json`, without a shell. Use the agent CLI's current working directory, not the board server's. Keep processing events while it runs. Log spawn failures and nonzero exits. Stop child processes when the event stream ends.
- **S2.32** Retry network failures, unexpected disconnects and HTTP 408/429/5xx every 10 seconds. At most 10 connection attempts per outage, including the first; successful connection resets the count. Log each retry; after exhaustion log failure and exit 1. Do not retry intentional stop, other HTTP rejections or invalid protocol data.
- **S2.33** `--harness`: `claude` (default, Claude Code) or `copilot` (Copilot CLI). Reject other values with usage and exit 1. Send `harness` to server; server defaults omitted value to `claude`, rejects invalid values with 400.
- **S2.34** Dialects live in `cli/agent/harnesses/claude.js` and `cli/agent/harnesses/copilot.js`; each defines executable, label and arguments. Claude's module owns permission rules and settings setup, called by `init` (CLI S2.10). Agent shares process capture and lifecycle handling. Claude emits JSON; Copilot emits JSONL. Log per S2.45; unparsable output is logged raw.
- **S2.45** `agent -v`, `--verbose` (repeatable; `-vv` = level 2; more than two = 2): log level. Default 0. Only with `agent`. Level 0: harness `duration` and `price` only. Level 1: also the prompt (S2.41) and the `response`. Level 2: also the raw harness stdout.
- **S2.35** On connect, before the first `ping`, server sends `welcome` `{ id, name }`. CLI reconnects (S2.32) with that name, so an automatic name (S2.26) stays the same.

## Build queue

- **S2.36** Server keeps one in-memory build queue: tasks `{ id, contextId, chapterId, sliceId, sliceName, builder, status, error, response, sliceUpdatedAt }` in add order. Stored `status`: `queued`, `running`, `done` or `failed`; `error`: text when failed, else `null`; `response`: the harness's `response` text of a finished build (done or failed), else `null`. `sliceUpdatedAt` holds the built definition's slice `updatedAt`, not queue or completion time; `null` until reported. A `sliceId` has at most one task. Done tasks stay as the slice's last result. Lost on server restart.
- **S2.37** Each builder runs at most one task. Server starts the builder's first `queued` task and sends it as `build` event `{ id, contextId, chapterId, sliceId, sliceName }` on: builder connect, task added for it, its previous task finished.
- **S2.38** Routes:

| Route | Body | Result |
| --- | --- | --- |
| `GET /api/build-queue` | | Tasks (S2.36), `Cache-Control: no-store`; changed build inputs follow S2.46 |
| `POST /api/build-queue` | `{ contextId, chapterId, sliceId, sliceName, builder }` | 201 task. Trim values; blank or missing: 400. `builder` matches a live `builder` session ignoring case, stored with its session name; none: 404. Slice with a `queued` or `running` task: 409; a `done` or `failed` task is replaced by a new one at the end |
| `DELETE /api/build-queue/:id` | | 204. Only `queued` or `failed`; else 409 |
| `POST /api/agents/:id/tasks/:taskId/done` | `{ response?, sliceUpdatedAt? }` | 204; task `done`, `response` and input timestamp stored |
| `POST /api/agents/:id/tasks/:taskId/failed` | `{ error?, response?, sliceUpdatedAt? }` | 204; task `failed`, `error` defaults to `Build failed`; input timestamp stored |

  Unknown task or session: 404. `done`/`failed` for a task not running on that session: 409.
- **S2.46** Report the `updatedAt` from S2.43's saved definition as `sliceUpdatedAt` on success or failure after preparation. If supplied, require a non-negative safe integer; otherwise 400. Queue reads compare it with the current stored slice timestamp, including dependency changes (SERVER.md S3.16). A differing timestamp on a done/failed task returns `status: "changed"` and `buildStatus: "done" | "failed"` without changing its stored outcome, timestamp, response, error, cost or timing. Queued/running tasks and unknown timestamps are not Changed. Changed results remain rebuildable; removal follows the original outcome.
- **S2.39** Builder disconnect or stop puts its running task back to `queued`, still assigned to the same name; it resumes when that name reconnects.
- **S2.40** On `build`, log `Building slice "<sliceName>". Task: <id>`. After S2.43, run the harness as in S2.31. Require exactly `{"success": <boolean>, "response": "<explanation>"}` as the harness response, with no extra fields or surrounding text. `success: true` reports `done`; `false` reports `failed` with `error` set to `response`. Both also send `response`. Invalid responses and fetch, write or harness failures report `failed`. The prompt identifies the slice and Chapter/Context, tells the harness to read `.em/slices/<sliceId>.json` and not the server, and defines the response contract. Log build and reporting errors to stderr.
- **S2.41** Before spawning a harness, log its name and prompt to the agent terminal from level 1 (S2.45). After exit, log nonempty stdout as S2.45 and stderr always, with separate harness and stream headers (S2.34).
- **S2.42** Preapprove file read, write, edit, grep and glob for both harnesses. Claude preapproves Bash `curl` to `http://localhost` and `http://127.0.0.1`, with any curl options and quoted or unquoted URLs; on Windows (`process.platform === 'win32'`), add Bash `curl.exe` and native PowerShell `curl`/`curl.exe` rules for those hosts. Keep Bash permissions for `gradle`, `./gradlew`, `gradlew`, `gradlew.bat`. Cleanup: `Bash(rm .em/.tmp/*)`, `Bash(rm -f .em/.tmp/*)`, `Bash(rm -rf .em/.tmp/*)` and, on Windows, `PowerShell(Remove-Item -LiteralPath .em\.tmp\*)`; command-text matching is not filesystem confinement. Claude uses `.claude/settings.json` from `init` (S2.10), not command arguments. Copilot exposes file tools and `bash`; preapproves `shell(curl)` and URLs `localhost`, `127.0.0.1`, not all shell commands/URLs. Add `powershell` and `shell(curl.exe)` only on Windows.
- **S2.43** Before each build, fetch `GET /api/model/chapters/:chapterId?slice=<sliceId>` ([S4.21](./SERVER.md#4-editing-api)). Check `chapter.id`, `chapter.context`, `context.id`, the requested slice ID and the presence of `chapter.lanes`. Replace `.em/slices/<sliceId>.json` in the agent CLI's working directory with the full response JSON. Do not launch the harness if preparation fails or the stream ends before launch.
- **S2.44** After saving the slice definition and before logging the harness prompt, log `Saved slice definition to "<path>". Task: <id>`. Do not log the definition contents.

## Modeling tasks

- **S2.47** Keep modeling tasks separate from manual Tasks and build queue. Fields: `{ id, scope, contextId, label, prompt, modeler, status, response, error, cost, currency, createdAt, startedAt, completedAt }`; status: `queued`, `running`, `done`, `failed`. Persistence and retention: S2.54.
- **S2.48** `POST /api/modeling-tasks` takes `{ agentId, scope, prompt }`; returns 201 task. Require non-blank prompt and live `modeler` session; builder: 400, missing session: 404. Scope: `{ type: "context", contextId }`, `{ type: "chapter", chapterId }`, `{ type: "slice", chapterId, sliceId }`, `{ type: "cell", chapterId, sliceId, laneId }` or `{ type: "element", chapterId, sliceId, laneId, elementId }`. Reject missing/extra scope keys with 400; missing target or mismatched containment: 404. Cell must be empty at submission and S2.50 scope resolution; occupied: 409. Derive Context and label from stored model.
- **S2.49** FIFO per modeler name, at most one running modeling task per modeler. Dispatch `modeling-task` event with task on add, connect, previous completion or heartbeat acknowledgment after stream backpressure clears. Only selected modeler receives it. Disconnect/stop returns running task to queued; same name resumes on reconnect. Re-execution may repeat partial edits; reread current model.
- **S2.50** `GET /api/modeling-tasks` returns newest-created first, including ties in `createdAt`; `Cache-Control: no-store`. Completion never changes display order. `GET /api/agents/:id/modeling-tasks/:taskId/scope` resolves current scope before execution. `POST /api/agents/:id/modeling-tasks/:taskId/done` or `/failed` takes `{ response?, error?, cost?, currency? }`; supplied text must be non-blank. Done requires response; failed requires response or error. `cost` is a non-negative number, else null. Returns 204 and starts next task. Missing task/session: 404; not running on caller: 409; builders: 400.
- **S2.51** CLI uses packaged `cli/agent/modeling-task-prompt.md`, current model API URL/port, authoritative scope IDs and user Markdown. Reuse harness lifecycle and logging (S2.31, S2.41, S2.45). Use slice-build XML format and parser: `<build><success>true|false</success><response>Non-blank text</response></build>`. Response contract follows user task and applies on every exit, including cleanup, non-model requests, errors, refusals and blocked work; user/skill formats never override it. Require exactly one build, success and response tag; no extra tags, Markdown fences or surrounding text. True: fully complete within scope; false: incomplete, blocked or outside scope. If command approval is required, stop and include the full command in the failure response; do not retry or switch clients/tools. Reports stay inside response; check tags, boolean and nonblank text before returning. Preparation, harness or response errors: failed with feedback. Log reporting errors; abort work when stream ends.
- **S2.52** Modeling prompt requires installed modeling skills and API-only model access; never direct `.em/model/` access or application-code builds. Read surrounding context; edit only selected Context Chapters and their contents, selected Chapter contents, slice elements plus its name and width, empty Cell elements or element-owned content. Context scope excludes Context metadata and other Contexts. Slice scope may add lanes and edit Chapter lane names, info and colors; these changes apply to all its slices but not their contents. Never remove lanes or change lane types. Do not change the slice's flow-end mark, info or position/order, or other slices' contents/metadata. Check automatic connections, propagation and linked-copy side effects; never change outside scope. Report unclear decisions, missing API tools and needed outside-scope work instead of guessing. Scope is prompt-guided, not API-enforced. Copilot permissions follow S2.42.
- **S2.53** Modeling prompt states directly: no `cd`; temp files only in S2.56's relative task directory; CLI owns setup/cleanup, overriding general skill temp instructions. No temp-directory creation or cleanup commands by the model. Read `model-navigation` before lookups; scoped endpoints, never whole-model downloads. Standalone `curl` requests (`curl.exe` in Windows PowerShell), quoted URLs; no chains/pipelines with preparation/parsing. Check HTTP status/error body before parsing.
- **S2.54** Persist modeling tasks in `<server root>/.em/.tasks/modeling.json`, not agent directories or model files. Keep all unfinished tasks and last 10 completions (done or failed), including prompts, responses and metadata. Save unfinished tasks as queued with null `startedAt`; restart restores them for S2.49 dispatch. Atomically replace history before accepting additions/completions; write errors leave memory unchanged and fail the request. Missing history starts empty; invalid history fails startup.
- **S2.55** Modeling prompt requires file-read tools for saved API responses and narrower scoped API reads for oversized results. No ad hoc scripts merely to inspect, filter or summarize JSON; keep prescribed bundled analysis scripts. Permissions stay unchanged; approval handling follows S2.51.
- **S2.56** Before each modeling harness run, CLI creates a unique `.em/.tmp/modeling-*` directory in the agent's working directory and supplies relative `{tempDir}` to the prompt. After execution, remove only that directory, also on failure or cancellation. Never remove shared temp root or sibling files. Preparation failure prevents launch; cleanup failure logs the path and fails the task, preserving prior feedback. No extra shell permissions.
- **S2.57** Modeling task status is explicit, never inferred from error presence. `response`: agent feedback on success or failure, else null. `error`: distinct technical failure, else null; never copy response into it, and store null for identical text. Preparation, harness and parsing errors use error only. Cleanup errors append to error without changing response. Builder tasks stay unchanged.
